# 002 · 载荷打包方案调研（**未落地**）—— node_modules 能否 bundle

> **状态：未落地（调研结论稿，2026-10-30）**。本文只记录结论与候选方案，**不代表已实施**；任何方案落地须另立需求、真机回归后才可升级为 ✅。

## 1. 问题的准确表述

先排除一个误判：**APK 构建/下载侧没有小文件问题**。载荷在 APK 内本来就是**单个**压缩归档（`assets/pi-web/pi-web.tar.gz`，且 `.gz` 被 `noCompress` 标记，禁止 aapt 二次压缩）。

3.4 万个小文件的真实代价在**首启**：Kotlin 侧 [`PayloadArchive.kt`](../app/src/main/java/org/fellow99/pi/PiDesktopAndroid/payload/PayloadArchive.kt) 把归档解压到 `filesDir`，34,705 个条目 = 3 万+ 次 create/write/inode 开销。因此问题应表述为：

> **能否减少首启解包（以及增量升级重解包）的文件数 / 体积？**

### 1.1 当前归档实测（2026-10-30 本机产物）

| 项 | 值 |
|---|---|
| 文件 | `app/src/main/assets/pi-web/pi-web.tar.gz`（80,181,888 B ≈ 80.2 MiB） |
| sha256 | `2625fbe157c343240fa90fe4281d6aa29ea04c9fc0fc429aac7a7d40ba3df0da`（`pi-web.version`） |
| 归档总条目 | **34,705** |
| 其中 `node_modules/` | **33,739（97%）** |
| `.next/` | 717（server 271 文件 + static 235 文件为主） |
| 其余 | 壳资产（extensions/skills/config/jitless/env.js/pi-web-launch.js）、bin、public、package.json |

node_modules 大文件数分布（Top）：

| 包 | 文件数 | 运行期必要性 |
|---|---:|---|
| `next` | 3,819 | 必需，但含 CLI / compiled 跨平台件 |

| `es-toolkit` | 1,374 | 服务端工具 |
| `openai` | 1,186 | 服务端用（整树复制，未按可达性裁剪） |
| `@earendil-works/*`（pi 内核） | 1,424 | **必需**，且被刻意 externalize（见 §3） |
| `caniuse-lite` | 840 | 构建期数据，运行期死重 |
| `prismjs` / `highlight.js` | 698 / 396 | 语法高亮（多套并存） |

| `@anthropic-ai` / `@aws-sdk` / `typebox` / `zod` | 666 / 617 / 693 / 489 | 服务端用 |

**裁剪残留（实测仍在归档内的跨平台死重）**：
- `@earendil-works/pi-tui/native/{win32,darwin,linux}/prebuilds/*/*.node` —— 6 个非 android-arm64 原生件；
- `@unrs/resolver-binding-win32-x64-msvc/`、`lightningcss-win32-x64-msvc/` —— 两个 win32 包目录；
- `sharp/dist` 的 **JS 绑定保留**（原生 `@img/*` libvips 平台包已被裁剪规则剔除，0 命中）——不调用即不加载，当前无害；
- 壳资产 `extensions/android-pty/vendor/node-pty/lib` 的 **JS 保留**（原生 `pty.node` 不在；PTY 按规划暂缓，`terminal.pty` 结构化 unsupported）。
- `.nft.json` 已 0 命中；source map 仅 19、`.d.ts` 仅 1（裁剪规则已覆盖大部分显性死重）。

> **CI 相关推论**：node_modules 被打进载荷，且裁剪靠平台无关的规则。Linux runner 上 `npm/pnpm install` 默认**不装** win32/darwin 的 optionalDependencies —— CI 产物里这些死重会自然消失，归档文件数/sha256 可能与 Windows 本机产物**不一致**。CI 必须把「归档条目数 / 体积 / 关键结构」作为 Release 前打印与核对项，不能盲目要求跨平台 sha256 相同。

## 2. 当前载荷是怎么来的（现状基线）

[`assemble-payload.mjs`](../scripts/assemble-payload.mjs) 流水线（对标 pi-desktop-ark 同名脚本）：

```
pi-web@v0.12.1 工作树
 ① 幂等打 6 条补丁（patches/v0.12.1/*.patch；--reverse --check 命中即跳；冲突 exit 2，绝不 3way）
 ② PI_DIST（build/pi-dist）：只引导 package.json/next.config.ts/public，.next 由重编镜像
 ③ 补丁标记断言（6 个 marker 必须进编译产物；缺 ⇒ next build --webpack 重编；仍缺 exit 2）
 ④ 裁剪复制 → build/payload-stage/pi-web
    · 产品面来自 build/pi-dist
    · node_modules 直接从 ../pi-web/node_modules 硬链接（Windows 整树复制 10min+ 不可行 ⇒ 同卷 link 零拷贝）
    · 按 crop-rules.mjs 剔除 nft.json / win32 SWC / sharp 原生 / node-pty / *.node
 ⑤ 追加壳资产：pi-web-launch.js、env.js、extensions、skills、config、jitless、
    next.config.runtime.js → 改名 next.config.js（绕开运行期 SWC）、bin/rotate-preview-secrets.js
 ⑥ 确定性 ustar+gzip（mtime=0、条目排序）→ assets/pi-web/{pi-web.tar.gz, pi-web.version}
 ⑦ bsdtar 独立第三方自检（逐块读取，防空名字头块回归）
 ⑧ 收尾还原 pi-web 工作树 pristine
```

运行期形态：Kotlin 解包到 `filesDir` → 进程内 libnode（`provision-engine.mjs` 投放 v24.22.1 small-icu）执行 `pi-web-launch.js` → 以 **Next 16 生产服务器**（`startServer({ dir })` / `NextServer` API 双候选）在进程内监听 loopback → 系统 WebView 加载。**平台封死子进程 Node**（`process.execPath` 是 APK），无 Termux、无 Chromium 随包。

## 3. 对照一：PI-Desktop（Electron）—— bundle 化的真实成功案例

工程：`D:\GitHub\AI\PI-Desktop`（0.21.x early preview；pnpm monorepo + Electron + Rust `host-core`）。
**它有 pi 运行环境载荷，而且就是 bundle 形态。**

### 3.1 机制（`packages/agent-runtime/scripts/bundle.mjs`）

- 依赖钉死 `@earendil-works/{pi-agent-core,pi-ai,pi-coding-agent,pi-mcp,pi-tui}@1.4.0`（pnpm `catalog:` + 3 条 `patches/*.patch`）。
- **esbuild 全量打包自己的 sidecar 入口** `src/sidecar.ts`：
  `bundle:true, platform:'node', format:'esm', splitting:true, minify:true`
  - 产物 = **1 个 `sidecar.js` + `chunks/[name]-[hash]` 若干 + 1 个 package.json（type:module）**——几十个文件，而非数万。
  - pi-coding-agent 整个被 esbuild **打进 chunk**（没有 external）。
  - banner 注入 `createRequire(import.meta.url)`，让 bundle 内残留的 require 仍可解析磁盘包。
  - `define: { PI_BUNDLED_NODE: "true" }` 通知 pi 上游扩展加载器当前为 bundle 形态。
- **原生/wasm 资产单独抽**：`@silvia-odwyer/photon-node` 的 `photon_rs_bg.wasm` 与 `image-resize-worker` 单独 bundle 到 `chunks/`（bundle 不了的 `.node/.wasm` 单独落地）。
- **原子安装**：先输出到 `mkdtemp` 暂存 → 旧产物 rename 成备份 → 新产物 rename 就位 → 失败自动回滚（防半成品 sidecar）。
- 扩展加载器重写（`src/extensions/loader.ts`）：用 `jiti/static` 在 bundle 内做 TS 转译；扩展 import 的内核模块经 **virtualModules** 注入（sidecar 已持有的同一模块对象）；`pi-tui` 给惰性空桩并上报使用的符号。
- 分发：electron-builder `extraResources` 把 `dist-bundle/` 复制为 `resources/agent-runtime/`；技能/插件以普通资源目录随包（`resources/skills`、`resources/plugins`）。
- 进程模型：Electron 主进程用 **Electron 自带 Node（ELECTRON_RUN_AS_NODE）spawn `resources/agent-runtime/sidecar.js`**，stdio NDJSON JSON-RPC；宿主能力反向代理给 Rust `host-core`。

### 3.2 为什么它能 bundle

| 条件 | PI-Desktop |
|---|---|
| 入口 | **自己写的** `sidecar.ts`（stdio RPC 程序），不是框架服务器 |
| 框架 | 不跑 Next；没有 manifest/worker/`{dir}` 磁盘树假设 |
| 扩展面 | 主动重写加载器（jiti virtualModules + pi-tui 空桩），自己接管模块身份 |
| 进程 | 可 spawn 独立 Node 进程 |
| 原生件 | 仅 photon wasm，单独抽 chunks |

## 4. 对照二：pi-web（上游）——「有 webpack，但刻意不 bundle pi 内核」

工程：`D:\pi-workspace\pi-web`（Next 16.3.8 + React 19；`npm run build` = `next build --webpack`）。

### 4.1 四个事实

1. **业务代码确实被 webpack bundle**：客户端 → `.next/static`（8.7 MiB hashed chunks）；服务端 → `.next/server`（236 个 .js，chunks 仅 5.6 MiB，路由级 bundle）。
2. **pi 内核被刻意 externalize**。`next.config.ts`：
   ```ts
   serverExternalPackages: [
     "node-pty", "undici", "web-push",
     "@earendil-works/pi-coding-agent",
     "@earendil-works/pi-agent-core",
     "@earendil-works/pi-ai",
     "@earendil-works/pi-tui",
   ],
   ```
3. **运行期按真实磁盘路径动态 import，且强制模块单例**（`lib/pi-sdk-internals.ts`）：
   ```ts
   // Loaded at runtime from the SDK's own files, never bundled: a bundled copy
   // would be a second module instance with its own classes.
   await import(/* webpackIgnore: true */ /* turbopackIgnore: true */ pathToFileURL(path).href);
   ```
   该文件自行解析 package.json 的 conditional exports、`realpathSync` 定位 SDK 目录，并做**身份校验**：MCP 扩展若不是同一模块实例（`createMcpExtension !== ...`）直接报错拒绝运行；`PI_PACKAGE_DIR` 被设置时也拒绝（只认与 pi-web 同一棵树里的 SDK）。
4. **没有 `output: "standalone"`，但 nft 追踪基础设施已存在**：配置只有 `outputFileTracingRoot`，`.next/standalone` 不生成；但每个路由产物旁已生成 `.nft.json`（@vercel/nft 文件级可达追踪，72 个）。实测默认 trace 很粗：去重后约 61.8 万文件（含全平台包），pi 内核 3,260 文件在列。无任何 esbuild/ncc/pkg 独立打包脚本；`bin/` 仅 CLI 启动辅助。

### 4.2 结论

> 在**不改 pi-web 源码契约**的前提下，把 node_modules 整体 bundle 掉不可行。
> 这不是 webpack 能力问题，而是 pi-sdk-internals 的「运行期文件系统加载 + 类单例断言」会直接拒绝第二份模块副本；Next 生产服务器自身也强依赖磁盘目录树（manifest、worker、`require.resolve`）。

## 5. 三方对比

| 维度 | PI-Desktop（Electron） | pi-web（上游） | pi-desktop-android（本工程） |
|---|---|---|---|
| bundle 对象 | pi 内核等 SDK 库 | 仅业务代码（app/components/lib） | 同 pi-web（继承上游契约） |
| 入口 | 自写 sidecar.ts（stdio RPC） | Next 16 生产服务器 | 进程内 Next 16 生产服务器 |
| pi 内核 | esbuild **打进** chunk | `serverExternalPackages` + 路径动态 import + 单例校验 | 同 pi-web（external，真实磁盘树） |
| 扩展面 | jiti virtualModules + pi-tui 空桩 | pi 扩展按真实文件 `import()` | 同 pi-web + 壳资产物化到 `PI_CODING_AGENT_DIR` |
| 进程模型 | Electron Node spawn 独立 sidecar | 普通 Node `next start` | **进程内 libnode，封死子进程 Node** |
| 原生件 | photon wasm 抽 chunks | node-pty（external） | libnode.so 走 jniLibs；pty 暂缓 |
| 部署产物 | dist-bundle（数十文件）→ asar/extraResources | `.next` + 完整 node_modules（无 standalone） | 确定性 tar.gz（34,705 条目） |
| 是否可直接借鉴 bundle | **不可直接移植**（除非放弃 Next、重写 UI 层） | ——（被约束方） | 受同一契约约束 |

**PI-Desktop bundle 路线对本工程不可直接移植**：它 bundle 的是「agent 内核（库）」，入口是自控的 RPC 程序；本工程的载荷核心是「Next 服务器 + pi-web 应用」，内核是被 Next 在进程内以 external 包形态 require 的，bundle 它要同时改 `serverExternalPackages`、pi 扩展加载契约、并满足类单例断言，风险集中在 Next 侧而非 esbuild 侧。

## 6. 候选方案（按风险排序）

### 方案 A：加狠裁剪规则（低风险，预计砍 40–60% 文件数）

纯流水线改动（`crop-rules.mjs` 增规则），不动运行期形态：

- 剔除纯构建期工具链：`eslint`、`eslint-config-next`、`@babel/*`、`caniuse-lite`、`browserslist` 数据等；
- 剔除重复语法高亮：`react-syntax-highlighter` 与 mermaid/prism/highlight 语言包去重（需先确认 pi-web 实际引用面）；
- 剔除各包 `__tests__/docs/examples/*.d.ts/*.map`；
- 补齐跨平台原生件：pi-tui 的 win32/darwin/linux prebuilds、`lightningcss-win32-*`、`@unrs/*win32*`（CI Linux 上多为自然不装，规则用于本机一致性）；
- 评估 `es-abstract` 多版本嵌套、`openai/@anthropic-ai/@aws-sdk` 整树中未触达的子路径。

**验证**：真机回归页面渲染 + agent 工具面（extensions/skills 加载、MCP、模型对话、导出、终端 unsupported 口径）；首启解包计时对比。
**风险**：误删运行期动态 require 的文件（pi SDK 有变量式 import）⇒ 必须真机全量回归，规则只增可回退。

### 方案 B：Next `output: 'standalone'`（中风险，收益最大，最正统）

- 在 `patches/v0.12.1/` 新增补丁给 `next.config.ts` 加 `output: "standalone"`（上游 `next.config.ts` 仍是构建期唯一权威）；
- 用 Next 内置 @vercel/nft 产出的 `.next/standalone`（只含被 trace 到的 server + external 包文件）替代「整树硬链接 + 黑名单裁剪」；
- 用 `outputFileTracingIncludes` 显式补 nft 漏追踪的动态面：pi SDK 的变量式 `import()`、MCP、extensions/skills、`pi-sdk-internals` 解析到的 glob；用 `outputFileTracingExcludes` 收紧跨平台/构建期件；
- 改 `assemble-payload.mjs` 的组装来源与启动方式（standalone 自带 `server.js`，或仍用现有 startServer 候选但 `dir` 指向 standalone）；
- 同步处理运行期 `next.config.js`（SWC 绕行）与 standalone 的衔接。

**前置事实**：nft 基础设施已在（每路由 `.nft.json` 已生成），但默认 trace 粗（61.8 万去重条目）⇒ 调优 Includes/Excludes 是主要工作量。
**验证**：必须真机全量回归（standalone 漏文件的典型现象是运行期 ERR_MODULE_NOT_FOUND，只在特定工具路径触发）。
**建议**：单独立项，先出一版 standalone 产物与现 tar.gz 的结构/功能 diff。

### 方案 C：asar 式归档直读（高风险，长期项，不建议现在做）

保持单归档、首启不解包，patch `fs`/`Module` 让 JS 从归档内读取（Electron asar 同思路）。worker / `.node` / 被 mmap 的件仍需落盘，兼容性需逐项验证，工程量大。**暂不实施。**

### 宿主侧（与 A/B 正交，不改载荷）

- 确认 `PayloadArchive` 按 `pi-web.version` 做增量解包（版本未变不重解；版本变原子替换——可借鉴 PI-Desktop bundle.mjs 的「暂存 + rename + 回滚」就位模式）；
- 批量落盘、减少 fsync；解包耗时与文件数写入日志/Release 核对项。

### CI 侧（属于需求 012-building-workflow）

- workflow 在 Release 前打印归档基线：**条目数 34,705 / 80.2 MiB（Windows 本机基线）**，CI Linux 产物允许差异但需显式打印并核对关键结构（`.next`、pi 内核路径、壳资产、6 个补丁 marker）；
- 不为本需求改变载荷形态（避免 CI 未立先引入真机回归变量）。

## 7. 建议与决策项

1. **本需求（001 GitHub Actions 构建流程）不改变载荷形态**，仅把体积/文件数门禁纳入 workflow 输出。
2. **载荷瘦身另立需求（建议编号 002-payload-slimming，注意与本文 docs 编号区分）**：
   - 第一迭代：**方案 A**（低风险裁剪规则 + 真机回归 + 首启计时）；
   - 第二迭代：评估并试做 **方案 B standalone**（nft Includes/Excludes 调优 + 结构 diff + 真机全量）；
   - 方案 C 搁置。
3. PI-Desktop 可借鉴的**非 bundle** 经验：产物原子就位（暂存/rename/回滚）、原生/wasm 单独抽离（与本工程 .so 走 jniLibs 同思想，互相印证）、即使全 bundle 仍需 electron-builder 层排除 test/example/map（说明规则裁剪永远是补充手段）。
