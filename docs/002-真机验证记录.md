## 过程记录（可复核）

1. **端口 15577 被占**：模拟器上同族探针应用（`org.fellow99.dsh.android` 等）已监听 15577 ⇒ Node 侧 `listen` 抛 EADDRINUSE ⇒ 事件循环清空 ⇒ `state=Exited`。探针改用 **15677**。教训与规划 §6.2 ⑰ 一致：**固定端口互抢是硬故障**，产品载荷必须 `listen(0)` 随机端口。
2. **Windows 宿主侧 15677 被占**：`adb forward tcp:15677` 在 Windows 侧连不通（本机其它服务占用该端口），换 **host 25677 → device 15677** 后稳定。取证脚本的教训：host 端口也要避开常用值。
3. **探针 v1 的 /facts 聚合端点挂死**：ARM 翻译层下 `spawnSync` 曾长期不返回，单线程事件循环被钉住，阻塞全部取证。v2 改为「独立端点 + withTimeout + 异步 spawn + 定时 kill」后全部收敛。⇒ 写进 specs：**诊断端点必须可超时、不可互相阻塞**。
4. **SSE 断言 bug**：首版 o3 页在第 3 个事件时断言 `data==='done'`（done 在第 5 个才发）误报 false；服务端 `curl -N` 复核为正确 event-stream。修断言后 SSE ✓。教训：**判据写错比能力缺失更常见**，先复核服务端再怀疑平台。

### 错误恢复路径（P1-5 文档半边）

- **Java/Kotlin 未捕获异常**：`PiApplication` 哨兵先把现场（时间/线程/异常/栈，≤16KB）原子写
  `filesDir/crash/last-crash.txt`，再交系统默认处置；下次启动 MainActivity 顶部横幅展示
  「上次异常退出（时间，异常类）」——用户引导 = 重开应用 + 查 app.log。
- **原生崩溃（SIGSEGV 等）**：signal 直接带走进程，Java 层不可拦截（berberis SEGV 即此类）。
  恢复 = 系统重启引导（Launcher 重开）+ tombstone（`/data/tombstones`）；错误页的「重启应用」
  按钮仅在进程存活时可达。此边界即能力清单 §F P1-5 的「至少写进文档」交付。

   （幂等键归解包 marker，不归 asset→cache 搬运）。
2. **singleTask extra 陷阱**：运行中 `am start --ez xxx` 走 `onNewIntent` 不走 onCreate ⇒
   selftest/crash-test 钩子需在两处都接（已修）。
3. **`am start --ez crash-test`** 的 extra 名是 `crash-test`（连字符），代码键名需兼容。
4. **`am crash <pkg>`** 在 API 37 打到 WebView 沙箱子进程（`com.google.android.webview:sandboxed_process0`），
   不经过应用 Application ⇒ 哨兵验证必须用应用内受控钩子。
5. **shell 不能启动非导出服务**（API 37："Requires permission not exported from uid"）⇒
   前台服务验证走 `runtime.keepAlive` 能力（应用进程内）。

## Phase 4 · O6 PTY 探针（2026-10-29，暂缓项重启评估）✅ 探针完成

> 规划 §14.2 O6：「PTY 可行性：应用域 open("/dev/ptmx") + 现成 node-pty android 产物有无」。
> 背景：ark（OHOS）应用域 /dev/ptmx 全 EACCES（无 devpts）；dsh（Android 同门）实测可开——本探针定分晓。
> 证据：`evidence/pty-selftest.json` + `evidence/pty-selftest.logcat.txt`（launch 窗口自检，debug 包）。

| # | 探针 | 结果 | 判读 |
|---|---|---|---|
| ① | `fs.openSync('/dev/ptmx','r+')` | ✅ **open 成功** | **应用域 SELinux 放行**——dsh 口径成立；ark 的「连 ls 都 EACCES」死路在 Android **不存在** |
| ② | devpts 挂载 / /dev/pts 枚举 | ◐ | devpts **已挂载**（`rw,seclabel,relatime,mode=600,ptmxmode=000`）；但 `ls /dev/pts` Permission denied（ptmxmode=000 ⇒ 目录元数据不可读） |
| ③ | slave 盲试 /dev/pts/0..5 | ❌ | `0:EACCES 1..5:ENOENT`——**纯 JS 无法 unlockpt/TIOCGPTN（无 ioctl 绑定）** ⇒ 纯 JS PTY 路线不通 |
| ④ | toybox `script` 桥 | ❌ 不存在 | 「script -qfc sh /dev/null」零原生件路线不通 |
| ⑤ | stty | ✅ /system/bin/stty | 终端属性通道在位（路线 A 的配套件） |

### 评估结论（交用户决策；本探针不改行为，terminal.pty 维持 unsupported）

1. **关键解锁已证实**：ptmx 可 open + devpts 在挂——ark 的 L1 死路在 Android **不成立**；「Android 与 ark 更严口径相反」实测坐实。
2. **纯 JS / 免原生路线全部排除**（③④）⇒ 复活**唯一路线 = 原生件**：node-pty android-arm64 自建
   （NDK + node headers @aosp-node-runtime 24.22.1 + node-pty 1.x；生态**无现成产物**——node-pty 源码分发，
   nodejs-mobile 生态无直接预编译件）。工作量估算：交叉编译流水线 + pty.node 接入 + spawn 语义改造
   （sh 子进程 setsid+TIOCSCTTY 由 node-pty 内部完成，spawn 通道 O5 已证）≈ **1–2 天工程 + 回归**。
3. **风险与边界**：模拟器为 userdebug 镜像（SELinux 口径可能宽于真机 user 版）⇒ ptmx-open 需真机复测核销
   （Termux 先例 + dsh 实测支持真机可开）；`ptmxmode=000` 由原生件 unlockpt 后可解（node-pty 内部走 ioctl）。
4. **建议**：维持暂缓现状（能力面 unsupported 不变）；若用户拍板复活，按路线 A 立项
   （node-pty 构建流水线 → android-exec pty 通道 → /api/terminal 联调 → 真机矩阵）。
