# Pi Desktop Android（`pi-desktop-android`） — 工程规划

> **一句话**：把 **Pi Desktop**（`pi-web` 前端 + `pi` agent）搬到 Android：应用**自己的进程**里用
> [`aosp-node-bridge`](d:/node-bridge-workspace/aosp-node-bridge/docs/000-工程规划.md)（Maven：`io.github.fellow99:node-bridge` +
> `io.github.fellow99:node-runtime`）拉起**真正的 Node.js 运行时**（`dlopen` + `node::Start`），在 Node 里起
> `pi-web` 服务端（同源 HTTP + SSE），主 UI 由**系统 WebView** 渲染 `http://127.0.0.1:<随机端口>/` ——
> **不带任何 Chromium/Electron 内核、不用 Termux、不用子进程 Node**，形态与职责分界**逐层对标 `pi-desktop-ark`**（HarmonyOS Edition）。

| 应用名 / 包名 | **Pi Desktop** / `org.fellow99.pi.PiDesktopAndroid`（2026-10-24 定稿；应用名与 pi-desktop / ark 品牌口径一致） |

### 0.2 证据标注口径

沿用 ark/bridge 的四标记，**不要把推断当实测**：

| 标记 | 含义 |
|---|---|
| ✅ **实测** | 本工程或可复核的一手证据（源码 `path:line` / 本机产物 / 真机日志） |
| 🔶 **沿用** | 沿用外部工程的一手实测（bridge 真机 R2、ark 真机记录），可信但**不等于本工程事实** |
| ⬜ **待验证** | 本工程必须自行实测后才能定稿（→ Phase 0 探针） |
| ⚠️ **冲突/风险** | 两份一手材料互斥，或存在已知硬阻塞，必须专项处置 |

**两条纪律**（逐字继承自 ark/bridge）：

1. `🔶 沿用` 不得作为对外承诺依据 —— Android 碎片化比鸿蒙更重（厂商 ROM、SELinux、WebView 内核版本），
   「bridge 探针机上成立」≠「目标机型成立」，**必须真机调一次**；
2. 凡涉及运行时可见性的结论，**观测点必须是应用域**：`adb shell` 域能读的文件，应用域未必能读。

### 0.3 非目标

- **不维护自己的 Node 运行时实现**：一切 `dlopen`/`node::Start`/线程/解包机制归 `aosp-node-bridge`；
- **不改上游 `pi` / `pi-web`**：只允许**幂等可反向**的补丁，按 ark 的补丁集移植（§9）；
- **不做浏览器**：WebView 只加载本机 loopback 服务；外链一律交系统浏览器（`shouldOverrideUrlLoading` 主 frame 拦截）；
- **不做子进程形态的 Node**（bridge §4.9 路线 C 封死）；**不引入 Termux / 外部 node 依赖**；
- **不申请** `MANAGE_EXTERNAL_STORAGE` / `REQUEST_INSTALL_PACKAGES` / `QUERY_ALL_PACKAGES`（bridge §9.4 同口径）；
- **v1 不做**：Android TV/ Wear / 横竖屏桌面级窗口管理、开机自启、自动更新、`:node` 独立进程形态（保留为 Phase 4+ 可选加固）。

## 1. 项目概述

### 1.1 一句话定义

`pi-desktop-android` 是一个 **Android 应用**：`MainActivity`（`launchMode="singleTask"`）启动时把库投进来，由库在
**应用进程内**跑起 Node，Node 里加载 `pi-web` 服务端（Next 16 运行时 + `pi` agent），监听 **loopback 随机端口**；
主界面是一个**系统 WebView**，它先显示应用内加载页，探活成功后 `loadUrl("http://127.0.0.1:<port>/")` 加载
**由本地服务渲染的**标准 Pi Web UI —— 同源、零 CORS、零 IPC、无头改写。

### 1.2 关键结论速览

| 维度 | 结论 | 出处 |
|---|---|---|
| 可行性 | **成立**：`aosp-node-bridge` 真机 R2 已全链路验证（JIT/WASM/worker/宿主桥），本工程是其规划文体内预告的首个消费方 | 🔶 bridge `002-真机验证记录.md` R2；bridge 规划 §1.3 |
| 运行时形态 | **进程内 `dlopen` + `node::Start`**（bridge 路线 A）；`process.exit` 后 Node **永久死亡** ⇒ 状态机含 `exited` 态 | 🔶 bridge 规划 §4.9/§5.2 |
| JIT | **Android 可用**（targetSdk 36 与 28 双 flavor 实测 `jit.wasm=ok`、热循环 15–18 ms）⇒ **不需要** ark 的 `--jitless` compat 主线 | 🔶 bridge R2；本工程须自证（O1） |
| 载荷 | **必须首启解包**：Android `assets/` 不是文件系统路径，ark 的 `resfile` 只读直读**不可平移**；由库 `archiveAsset` + SHA-256 幂等解包 | 🔶 bridge 规划 §4.8 #1/§5.5 |
| 宿主桥 | **JNI 直调 + Kotlin Handler**（比 ark 的文件信箱传输层更简单、更低延迟）；能力名沿用库冻结 v1 清单 | 🔶 bridge 规划 §5.4；ark `001-能力复刻评估.md` §B.2#26 |
| 数据面 | 沿用「同源 HTTP + SSE」：`/`（SPA）、`/api/*`、SSE 直连本地服务；loopback 免密 | ark 规划 §4/§6.2 |
| 渲染 | 系统 WebView（无 Chromium 随包）；**必须** `networkSecurityConfig` 放行 loopback 明文 + `setDomStorageEnabled(true)` | 🔶 bridge 规划 §6.3 |
| 后台 | **前台服务可行**（Android 能力增量，ark 被封死）⇒ 长会话可保活，Phase 2+ 落地 | 🔶 bridge 规划 §1.2/§4.4 |
| 体积 | 库侧增量 ≈ 35–45 MiB（AAR 压后）+ 载荷（裁剪后 tar.gz 预估 70–90 MB 级，随 ark 口径） | 🔶 bridge 规划附录 C；ark 规划 §7.2 |
| 上游补丁 | 移植 ark `patches/v0.12.1/` 的 6 条，其中 3 条需 Android 化改写（§9） | ark `patches/README.md` |

## 2. 背景与对标

### 2.1 为什么对标 `pi-desktop-ark`

1. **形态同构**：ark = 「宿主 + 系统 WebView + 进程内 Node + 端上 pi-web 服务」，Android 侧由
   `aosp-node-bridge`（bridge 规划自称 ohos 版的「Android 同构实现」）补齐了运行时层，宿主层可逐层映射；
2. **文档与纪律可复用**：ark 的宪法 10 条、spec/plan 规格、能力复刻评估方法、补丁流水线、devtest 套件，
   全部可平移为本工程的底稿；
3. **插件与补丁直接对标**（用户需求）：ark 的同名顶替扩展（exec/search/runtime/workspace-roots）与
   `patches/v0.12.1/` 补丁集是经真机验证的资产，本工程移植并 Android 化；
4. **两个能力增量有明确诉求**：git（ark 已有实现可同步）与 pnpm（ark 未做，Android 侧新增，见 §11）。

### 2.2 Ark → Android 结构映射总表

| 层 | pi-desktop-ark（HarmonyOS） | pi-desktop-android（本工程） | 差异与风险 |
|---|---|---|---|
| 应用入口 | ArkTS `UIAbility`（EntryAbility，`launchType: singleton`） | `MainActivity`（`launchMode="singleTask"`） | 语义等价；单实例是硬约束（端口互抢，bridge §6.2 #1） |
| 主 UI | ArkWeb `Web` 组件（`domStorageAccess`+`databaseAccess` 必开） | 系统 `WebView`（`setDomStorageEnabled(true)` + JS 已默认开） | Android 需 **`networkSecurityConfig`** 放行 loopback 明文（ark 无此概念）⬜ P0 探针 |
| 加载页/错误页 | ArkTS 视图叠加（非 `data:` 页）+ 诊断面板 | 原生视图（Compose 或 View 体系）叠加 + 诊断面板 | 对标 ark「失败可见」四态 |
| 运行时库 | `@fellow99/node-bridge` ohpm HAR（ArkTS API） | `io.github.fellow99:node-bridge:0.2.0`（Kotlin `StateFlow`） | API 形态更顺：轮询 → Flow 推送；显式 `markRunning/markFailed` |
| 引擎包 | `@fellow99/node-runtime@24.2.0` ohpm | `io.github.fellow99:node-runtime:24.2.0` Maven（`runtimeOnly`） | `libnode.so` 由 AAR 合并进 APK；16 KB 对齐门禁已过 🔶 |
| 引导方式 | NAPI 模块 + `dlopen`（只认裸名） | `System.loadLibrary("node")` + `dlsym`（裸名/绝对路径皆可） | ✅ Android 更简单（bridge §5.10 ①） |
| JIT 形态 | 编译期固定 compat（`--jitless`），jitless 纯 JS 兼容层 | **主线 JIT**（真机已验）；`jitless` 仅诊断开关；载荷侧 jitless 兼容层保留（WASM 在位时为 no-op） | ⚠️ WebView 无关；V8 W^X 风险已被 bridge R2 证伪，但**机型矩阵待扩**（O1） |
| 载荷投放 | `resfile/pi-web/pi-web.tar.gz` → Node 侧解包（`filesDir/payload/<sha12>/`） | `assets/pi-web/pi-web.tar.gz` → **Kotlin 侧解包**（bridge `archiveAsset`，`filesDir/node-bridge/payload/`） | 解包主体从 Node 挪到 Kotlin（bridge §5.5）；首启耗时 ⬜ P0 探针 |
| 就绪判定 | Node 写 `pi-web.ready.json` marker + stdout `PI_WEB_READY` 行；ArkTS 读 marker 取真实端口 | **同一份 Node 侧代码**（`pi-web-launch.js` 移植）；Kotlin 读 marker + `markRunning()` | 纯 Node 代码，近乎原样平移 |
| 宿主能力桥 | 文件信箱传输（真机 2 ms 往返） | **JNI 推送 + Kotlin Handler**（库原生链路，R2 已验 `host.echo` 全链路） | 本工程是「主路」，不再需要信箱降级 |
| 宿主能力清单 | 库冻结 8 能力名（perm/picker/openExternal/notify/facts…），ArkTS 实现 | **同名能力**，Kotlin 实现：SAF 选择器、`Intent` 外链、`NotificationManager`、`PackageManager` 预检 | 能力语义对标 ark `104-host-capabilities` 规格 |
| 工作区根 | `PI_HOS_ROOTS`（桌面/文档/下载授权目录 + 沙箱） | `PI_ANDROID_ROOTS`（app-specific 外存真实路径 + SAF 持久化授权树，§5 第 10 条） | ⚠️ Android 存储分区模型差异最大的一处（⚠️ R6） |
| 鉴权 | loopback 免密（路线 ①）；回退局域网+密码+Cookie 注入 | 同 ark：**首选 loopback 免密**；密码回退用上游 `PI_WEB_PASSWORD` | 上游机制相同（proxy.ts / request-security.ts） |
| 端口 | `listen(0)` 先探后用 + marker 回传 | 同左（Node 侧代码共用） | 端口冲突 ⇒ 进程 abort 的教训直接继承（⑰⑱） |
| 日志 | `payload/app.log`（自己的通道）+ `node.log`（库）双通道；`hdc fport` + `curl /log` | 同双通道；`adb forward` + `curl /log`；logcat 第三通道 | fd1/2 指向 `/dev/null` ⇒ 库已建 pipe+reader 🔶（bridge §5.7） |
| 取证通道 | snapshot_display / uitest / rport / hilog | `adb shell screencap` / `adb shell input` / `adb forward` / `logcat -b crash` | 语义等价（bridge §4.8 #11） |

### 2.3 平台差异的落地影响（消费方视角，引 bridge §4.8）

| # | 差异 | 对本工程的要求 |
|---|---|---|
| 1 | `assets/` 不是路径 | 载荷必须解包；**不要**出现任何「拼 assets 路径给 fs」的代码 |
| 2 | 原生库加载走 `System.loadLibrary` | 宿主不手写 `dlopen`；全部交给库 |
| 3 | JIT 门槛 = 平台 W^X 策略（无 ACL） | 无审批流程；把「机型 × Android 版本」做成验证矩阵（§14 O1） |
| 4 | 后台常驻可行 | 前台服务是**可选能力**，默认不开，用户显式启用（通知常驻） |
| 5 | 进程内 Node 不可重启，`:node` 进程可 | v1 接受「崩溃=终态」UX（同 ark）；`:node` 留作 Phase 4+ |
| 6 | `spawn` 受限 | 一切子进程语义只做「能力标志」，不依赖 `exit/close`；`bash` 用常驻 shell + 哨兵行（同 ark） |
| 7 | JNI 宿主能力面更宽 | 能力清单可超出 ark 8 项（如 `share.share`），但**新增能力名须先与库契约对齐** |
| 8 | 主线程做重活 ⇒ ANR | 启动/解包全在库的 detached 线程与 Kotlin 协程；主线程只碰 UI |
| 9 | 产物核对查 APK 不查磁盘 | `unzip -l` / `zipalign -c -P 16` / `bundletool dump` 纪律沿用 |

## 3. 目标与原则

### 3.1 目标（对标 ark 规划 §3.1 七目标 + 本工程两项增量）

1. **能起**：APK 可安装启动，进入 Pi Desktop 窗口，无白屏、无闪退；
2. **能用**：Web UI 全功能 —— 会话管理、发消息、**SSE 流式**、工具调用可视化、审批交互、上下文/成本、主题、多语言；
3. **能持久化**：会话 JSONL 落应用沙箱，重启应用后仍在；
4. **能配模型**：Models 面板可填 API Key / 登录，凭据落沙箱（`auth.json` 0600）；
5. **能用工具**：文件读写/编辑/列目录、`bash`/`find`/`grep`（同名扩展）、工作目录选择与授权；
6. **能用 git**：`android-git` 扩展提供本地仓库全流程（init/status/add/commit/branch/…，对标 ark 23 工具面）；
7. **能用 pnpm**：`android-pnpm` 扩展提供依赖管理（install/add/remove/list/why/store），可从 registry 拉包（⬜ 网络/脚本策略见 §11）；
8. **失败可见**：加载页阶段文本 + 错误页 + 诊断面板 + `adb forward` 证书端点，任何失败可截图可断言；
9. **能分发**：APK/AAB 构建可复现，合规清单（§17）可逐条核销。

### 3.2 设计原则（继承 ark 宪法 10 条，A1–A10）

| 原则 | 展开 |
|---|---|
| **A1 一切经 HTTP** | 前后端只通过同源 HTTP/SSE 通信；不加 JavascriptInterface 桥、不引入 IPC 载体 |
| **A2 壳薄、契约硬** | Kotlin 只做「启动 / 观测 / 宿主能力 / 渲染」，业务全在 Node 侧 |

## 6. 鉴权与安全边界

### 6.1 路线（对标 ark §6，上游事实逐条已核）

| 路线 | 做法 | 前置条件 | 代价 |
|---|---|---|---|
| **① loopback 免密（首选）** | 服务端只监听 `127.0.0.1:<随机端口>`，不设 `PI_WEB_PASSWORD`；WebView 加载同源地址 | WebView cleartext 放行（§5 #2 ⬜）；上游对 loopback 的放行逻辑已核（ark §6.1） | 无认证；暴露面 = 同机其它应用（Android 沙箱 UID 隔离下风险低） |
| **② 局域网 + 密码（回退，v1 不做）** | 绑 `0.0.0.0` + `PI_WEB_PASSWORD` 强随机 | 用户显式开启；上游 Basic/Cookie 机制原样可用 | 局域网暴露面；明文 HTTP 风险（上游 README 警告同源） |

### 6.2 端口与单实例（硬约束 ⑰⑱ 继承）

- 端口必须 **随机**（`listen(0)` 先探后用）+ **singleTask 单实例**；端口被占 ⇒ `EADDRINUSE` 未捕获异常 ⇒ 进程 abort
  （ark 真机实证 🔶，`docs/ACL配置.md` §3.1）；
- 载荷自装异常兜底 + **独立 `app.log` 通道**（stdout 会被 WebView/logcat 混流，⑱）；
- Android 特有：`WebView` 与 Node 同进程 ⇒ 无 ark「loopback 隔离」问题；跨进程场景（`:node`）Phase 4+ 另议。

## 11. pnpm 能力：`android-pnpm`（本工程新增，ark 未有）

### 11.1 需求与形态

| 项 | 决策 |
|---|---|
| 需求来源 | 用户明确要求「有 pnpm 能力」：agent 应能在设备上为项目安装/管理 npm 依赖 |
| 为什么是 pnpm | 内容寻址 store（`<filesDir>/pnpm-store`）跨项目硬链接复用，节省沙箱空间 —— 对设备存储友好；monorepo/workspace 支持好 |
| **形态（唯一可行路线）** | **进程内 vendored pnpm**：把 pnpm 官方单文件 bundle（`pnpm.cjs`，vendored 随包）载入**同一个 Node 进程**，以 pi 扩展形式注册工具面 —— **不做 PATH shim、不 spawn node 跑 CLI**（Android 无 node 可执行文件可 spawn；`process.execPath` 是 APK， ark §2.3 同款事实） |
| 工具面（v1） | `pnpm_install` / `pnpm_add` / `pnpm_remove` / `pnpm_list` / `pnpm_why` / `pnpm_store_status`（对标 harmony-git 的「注册工具」模式，`pi.registerTool`） |
| 工作目录围栏 | 仅限 `PI_ANDROID_ROOTS` 内的项目；node_modules 写入项目目录（外存真实路径可写） |
| store | `<filesDir>/pnpm-store`（content-addressable；跨项目复用；设置项可清） |
| 网络 | registry 直连（`INTERNET` 权限）；支持 `HTTP(S)_PROXY`/`NO_PROXY` 环境变量（上游 pi-web 同款语义）；离线模式 = `PI_OFFLINE=1` 时工具面降级为只读（list/why/store） |
| 脚本策略 | **默认禁用生命周期脚本**（preinstall/postinstall…）：spawn 受限（bridge §4.4）⇒ `--ignore-scripts` 语义为默认并如实写进工具描述；需要脚本的包如实报「该包在设备上不可完整安装」 |

### 11.2 风险与降级

| # | 风险 | 处置 |
|---|---|---|
| R8-1 | pnpm 内部对 `child_process` 的依赖面（bin 链接、`pnpm run`、prepare 生命周期）在 spawn 受限下的行为 | Phase 3 探针：vendored bundle 在设备上跑 `install --ignore-scripts` 一个真实小包；逐项记录可用/不可用 |
| R8-2 | bin 链接（`node_modules/.bin`）的 shebang 不可执行 ⇒ 项目脚本跑不起来 | 能力面定位为「**依赖管理**」而非「脚本运行器」；`pnpm_run` v1 只支持 pnpm 内建命令（`--version` 等），不做任意脚本执行 |
| R8-3 | pnpm bundle 体积（≈8–10 MB） | 计入载荷体积账；如超预算，评估按需 jambundle 或降级 npm-in-process |
| R8-4 | `@pnpm/*` 程序化 API 不稳定 | 锁版本 + vendored bundle + 冒烟测试（devtest `pnpm.mjs`） |
| 降级链 | pnpm bundle 不可行 → ① 改 npm（同样 in-process vendored）→ ② 仅离线 tarball 安装（`file:` 源） | 逐级登记，不静默 |

### 16.3 构建流水线

```bash
# ① 组装载荷（宿主机 Node；干跑→应用）

# ② 构建 APK
./gradlew :app:assembleDebug                 # 或 assembleRelease（签名材料本地，不入库）

# ③ 装机与取证
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n org.fellow99.pi.PiDesktopAndroid/.MainActivity
adb forward tcp:15577 tcp:15577 && curl -s http://127.0.0.1:15577/facts   # 端到端证书
adb forward tcp:<port> tcp:<port> && curl -s http://127.0.0.1:<port>/log  # 载荷日志尾（端口从 marker/诊断面板读）
adb logcat -s NODE_BRIDGE:V AndroidRuntime:E DEBUG:V
adb shell run-as org.fellow99.pi.PiDesktopAndroid cat files/node-bridge/node.log | tail -50  # debug 包
# 产物核对：查 APK 不查磁盘
unzip -l app-release.apk | grep '\.so$' ; zipalign -c -P 16 -v 4 app-release.apk | tail -3
```
